    microSD storage and its tests¶

    Phase 1 reads and writes the library on a microSD card over 4-bit SDIO, driven from a PIO program (not SPI). The firmware talks to it through hal_storage.h (card, raw sectors, mount) and the portable file API nfs.h (files and directories); see ADR-0006 and ADR-0008.

    Card format decision¶

    • Project format: exFAT, 128 KB clusters, aligned to the card's allocation unit. Reasons: files over 4 GB, SDXC cards are exFAT natively, and large clusters keep the FAT small and reads sequential.
    • FAT32 must mount as a fallback. The Phase 1 card arrived as FAT32 and every test except the format test runs on it unchanged.
    • The layout is an MBR with one exFAT partition (type 07) starting at the card's allocation unit and a data area aligned the same way, which is what the SD Association formatter makes.
    • Do not reformat the card on a PC or phone. Operating-system formatters pick their own cluster size and ignore the card's alignment. If you must, use the SD Association's SD Memory Card Formatter, which keeps the alignment. The firmware only formats when you ask (test 9).
    • 128 KB clusters waste space on small files (cover art) but make audio-heavy libraries fast; the numbers are in ADR-0008 and should be revisited with the measured results below.

    Library and resource use¶

    • Driver: carlk3's no-OS-FatFS-SD-SDIO-SPI-RPi-Pico, release v3.6.2 (Apache-2.0), a git submodule in lib/. After cloning run git submodule update --init --recursive. Its FatFs is used on the RP2350 (the host build uses the vendored FatFs); the FatFs configuration is platforms/rp2350/ffconf/ffconf.h, kept identical to the host's by a build-time check.
    • PIO / DMA: the SD driver owns pio1 (two state machines), two DMA channels claimed dynamically, and shares DMA_IRQ_0. The Wi-Fi chip and the click-wheel receiver land on pio2. If something else has claimed a state machine on pio1 the card refuses to start with a clear error instead of misbehaving.
    • Clock: the PIO program needs 4 PIO cycles per SD clock, so the SDIO clock is clk_sys / (4 x divider) = 125 MHz / (4 x 2) = 15.625 MHz by default (an integer divider; see the observations below). It can be changed at run time (hal_storage_set_bus_clock).
    • High Speed: the card says 25 MHz in default-speed mode (CSD TRAN_SPEED 0x32). Faster clocks need the card switched to High Speed (command CMD6). The driver library never sends it; the HAL does (hal_storage_enable_high_speed) using the library's low-level calls, and refuses clocks above 25 MHz until it has succeeded.
    • Write safety: writes are locked by default. Only the tests that need them unlock writes, for as long as they run, and always lock again and delete their files (even after a failure or q). In the runtime firmware one other piece of code opens the lock: the settings save, for the length of one save and only for paths under /.neupod (an nfs write scope; Bluetooth). Before unlocking, a test reads 16 MB of the card twice and compares; test files are created exclusively (an existing file is never overwritten; the test stops and tells you).
    • Write-fault latch: the driver library ignores the card's status after a write and can leave the card waiting for data after a failed write. The HAL therefore checks the card status after every write, and after any failure refuses all further writes until the card is re-initialised; test cleanup re-initialises and remounts first, and if that is impossible it leaves writes locked and lists the files to delete by hand.
    • Free space is computed with a full scan of the FAT (the stored FAT32 hint is not trusted), so it is slow on a big FAT32 volume; the time is printed.
    • Stack: the main stack is 4 KB for the storage test (the most core 0's scratch RAM bank can hold); the lowest free stack seen is printed after each test.

    Playlists, play counts and On-The-Go (design review LB-7)¶

    Two files besides ratings.bin, both written by the storage task under the same nfs write scope (/.neupod only), the same hardware write lock discipline, and always through a temp file that is synced and then renamed over the old one (the card does not rename over a file, so the old one is unlinked first; a power cut leaves the old file, or a complete temp file that the next read picks up; a partial temp file fails its check and is ignored). Only the builds with NEUPOD_ART_HIRES (hosted, Y2, PSRAM boards) keep them; the frozen Pico 2 W compiles them out.

    File What Format Card refuses writes
    /.neupod/plays.bin (plays_store.[ch]) counted plays and "last played" per track, with the path, title and artist the smart lists show binary: NPPL, version 1, serial, count, entries (key = path + size hash as for ratings, plays u16, last u32, stamp u32, three length-prefixed strings), CRC-32. 128 entries; the fewest played goes first, a rated one last RAM only, retried every 30 s (plays_persistent())
    /.neupod/otg.m3u8 (playlist_service.c) On-The-Go an ordinary UTF-8 playlist (#EXTM3U, #EXTINF:secs,Artist - Title, absolute path), ending in # end; at most 100 entries; add, remove and clear rewrite the whole file the add says "Card is write-protected" (nothing is kept in RAM)

    A play is counted once per track start when half of it was actually heard (time spent playing, so a seek does not count), 30 s if its length is unknown, or when it ends by itself after 3 s (play_tracker.h). Paths of 96 bytes or more are not tracked in plays.bin. Ratings stay in ratings.bin (a hash): Top rated lists the tracks the plays store knows, which a rating of four stars or more adds (a rating made before this feature appears once the track is played or re-rated). .m3u / .m3u8 files are only read, from /, /Playlists and /Music (not their sub-folders).

    Music library index¶

    Index format 3 (12 Nov 2026): sort keys skip a leading "A " / "An " as well as "The "; an older index is "needs rebuilding" and the Music lists rebuild it by themselves. Playlists add two files under /.neupod (below).

    The Music screens read an index of /Music that the firmware builds on the card itself (ADR-0017; screens: UI).

    • Where and how. /.neupod/lib/: 13 immutable files plus a manifest (about 8 MB for 100,000 tracks, roughly 90 bytes a track), each written once per build, the manifest last. A build goes to /.neupod/lib.tmp/, is synced, and replaces lib with two renames (lib to lib.old, lib.tmp to lib); a power cut leaves the old library or the new one (lib_recover() settles an interrupted swap the first time the index is opened after boot). A failed or cancelled build deletes lib.tmp and leaves the old library.
    • Writes. The index is the second thing in the firmware that unlocks card writes, after the settings save: only the storage task, only for the length of a build, and only under /.neupod (the nfs write scope; every folder-tree change is a real nfs_mkdir / nfs_unlink / nfs_rename, which nfs itself gates; /Music is never written). Nothing else in the library writes. A write-protected card is answered up front with "Library needs a writable card", before anything is attempted; a card that is full says so (Card is full).
    • When. The first time a list is opened with no index on the card, and Music > Update Library; never in the background, and only with nothing playing (the scanner borrows the audio core's decoder memory as its scratch, 99 KB, and refuses to start while anything plays or is paused). A Play press, a folder listing, Cancel or Menu stop it at the next file. Shutting the firmware down during a build is safe for the same reason a power cut is.
    • What it costs. Static RAM (RP2350 Release, measured): nothing for the reader and the row window (they share the Files screen's 20 KB listing buffer); +760 B for the service's bookkeeping and path cache, the queue and the resume path (free SRAM 14,504 B to 13,744 B). Flash: +40.6 KB: the library itself (about 28 KB of scanner, reader, sort and collation that L1 did not link yet) and about 13 KB for the lists, the service, the range queue and the screens. Reading: browsing keeps the audio ring topped up between rows; the reader holds 11 files open and a 4 x 2 KB page cache.
    • How long a scan takes. Host figure (POSIX files in the simulator, warm cache): 276 tracks in 131 ms, 1,016 tracks in 322 ms; L1's 100,000-file run on a FatFs disk image: 12 s. On the card it is not measured yet (the bench has not run it). Estimate from the ADR's costs (0.2-0.4 ms per directory entry, 10-20 ms to open and parse a file) plus about 60 small index and run files to create: about 260 FLACs in 5 to 8 seconds, 5,000 tracks in about 1.5 minutes, 100,000 in half an hour. The progress screen counts files; the sort and write at the end add a second or two without a counter.
    • The Y2 testbed. The Y2 firmware opens the card read-only (O_RDONLY) and only reopens it O_RDWR | O_SYNC while the library or the settings store holds the write lock, so no change to the Y2's storage is needed for the index to be written, and none was made. What it does need: the card's write-protect switch off (a write-protected card is opened read-only and the screen says Library needs a writable card); nothing else mounting the same card at the same time (the firmware's FatFs and a kernel filesystem driver writing one volume would corrupt it; the Y2's rootfs does not mount the card: its mdev.conf only sets the node's permissions and its fstab has no card entry; the rescue diag.sh is the one thing that mounts it, on demand, so check before adding an automounter); and patience, since O_SYNC makes every write wait for the card (a build is many small writes, so the Y2 will be slower than the estimate above). The boot line read-only is the default lock, not a mount option.

    Rules carried into the final board (3 Nov 2026)¶

    • SD clock from integer dividers only.
    • Multi-block reads capped at 128 blocks (NEUPOD_SDIO_MAX_READ_BLOCKS, platforms/rp2350/hal/hal_storage.c): in v3.6.2 a 256-block read writes the DMA list terminator one entry past dma_blocks[]. To be reported upstream to carlk3 (no-OS-FatFS-SD-SDIO-SPI-RPi-Pico).
    • A GPIO-controlled load switch on card VDD is a final-board requirement, so a card wedged mid-transfer can be power-cycled.

    Memory allocation policy¶

    The newlib heap is only about 33 KB (static RAM fills the rest) and the Pico SDK's malloc wrapper panics on failure instead of returning NULL (to be replaced by a wrapper that returns NULL and logs, per the design response of 3 Nov 2026; not built). FatFs with FF_USE_LFN 3 allocates scratch buffers as large as a cluster (dir_clear, up to 32 KB; 128 KB clusters on large exFAT cards) and relies on NULL to halve the request, so the first mkdir on the bench ended in "Out of memory".

    app/storage/ff_alloc.c therefore replaces the library's ffsystem.c (the RP2350 build removes it from the library's source list in platforms/rp2350/CMakeLists.txt; lib/ is untouched, the host build uses the same file). ff_memalloc returns NULL for anything above NEUPOD_FF_ALLOC_MAX_BYTES (4 KB, app/storage/ff_alloc.h) and otherwise calls the real, non-panicking malloc, so FatFs falls back to a 4 KB buffer or its window buffer. Mutex functions are not provided: FF_FS_REENTRANT is 0 and the build fails if it is turned on. Host test: tests/test_fatfs.c.

    Besides FatFs the only newlib-heap callers in the firmware image are the Bluetooth firmware download (about 1 KB, once at boot) and newlib's one-off stdio setup; core 1 never allocates (checked by tools/check_core1_closure.py).

    Running the tests¶

    git submodule update --init --recursive
export PICO_SDK_PATH=$HOME/pico/pico-sdk
scripts/build.sh rp2350
scripts/flash.sh rp2350 storage_test
scripts/console.sh      # type the keys here (the PC's serial console), not on the Pico
    Key Test Writes?
    1 Detect: card identification, CID/CSD/SD status, sector 0 No
    2 Mount: file system type, cluster size, label, serial, total/free space No
    3 List: recursive listing of the root, depth 2, capped at 200 entries No
    4 Integrity: 16 MB pseudo-random file round trip across a remount, then a 2 MB raw-sector round trip inside a file the test allocated Under /neupod-test/
    5 Sequential speed at 512 B, 4 KB, 32 KB, 128 KB blocks, read and write Under /neupod-test/
    6 2000 random 4 KB reads (latency average/min/max/p99), with and without fast seek Allocates under /neupod-test/
    7 Streaming: 32 KB every 20 ms for 10 s, counts missed deadlines Allocates under /neupod-test/
    8 Clock sweep: steps the SDIO clock up until an error, suggests a setting. Run it on its own; it needs /neupod-test not to exist beforehand Raw sectors inside one file under /neupod-test/
    9 Format the card: MBR plus one exFAT partition (needs typing YES) Erases everything
    a Runs 1-7 and prints a summary; never runs 8 or 9 as above
    q Stop the running test
    c Clean up leftover test files: lists /neupod-test/, then (after y) deletes only pattern.bin, raw.bin, speed.bin, sweep.bin and the directory if empty; never part of a Deletes under /neupod-test/

    Before any write test the card must have at least the test's size plus 64 MB free. Everything is written under /neupod-test/, which is created if missing and removed again if it was created by the test. A full run of 1-8 takes a few minutes (estimates: test 4 about 15 s, test 5 about 40 s, test 6 about 10 s, test 7 about 15 s, test 8 about 20 s); test 9 on a 64 GB card can take a minute or more.

    Test 8 allocates one contiguous file with the file system at the safe clock, then at each higher clock does only a read-only soak (4 MB read twice plus 100 status queries) followed by raw writes inside that file; the file system is not touched until the clock is back to normal. A failure at a test clock cannot damage the file system, only that file.

    Test 9 shows the card name and capacity, the current volume (type, label, space used), warns that all data will be erased, including other partitions such as a Linux root file system, and only continues if you type exactly YES and press Enter. It writes a partition table with one exFAT partition starting at the card's allocation-unit boundary, creates exFAT with 128 KB clusters aligned the same way, and labels it NEUPOD; then it remounts and shows test 2's output.

    On the PC, scripts/build.sh host builds the same menu as build/host/hal/host/storage_test over a disk image (NEUPOD_DISK_IMAGE) and a files directory (NEUPOD_FS_ROOT, default build/host/fsroot). Mount, raw-sector, clock and format tests are skipped there.

    Observations and open items:

    • exFAT with 128 KB clusters fixed the slow reads. On FAT32 with 2 KB clusters FatFs splits every transfer at cluster boundaries (at most 4 sectors per disk call), and the driver pays a read command plus a stop command per call. With 128 KB clusters, reads went from 3.8 to 7.3 MB/s, and random reads no longer need fast seek (1.27 ms either way).
    • Streaming is comfortable: 32 KB every 20 ms (1.64 MB/s, about 2.7× FLAC 24/96) with 76 % headroom.
    • Library bug, worked around: carlk3 v3.6.2 rp2040_sdio_rx_start() writes its DMA list terminator one entry past dma_blocks[SDIO_MAX_BLOCKS * 2] for a 256-block read, wedging the driver. FAT32 with 2 KB clusters never triggers it; exFAT with 128 KB clusters does on every 128 KB read. The HAL splits reads into chunks of at most 128 blocks (guarded_read in hal_storage.c), and a failed read latches the write fault so the card is re-initialised before any further write. Worth reporting upstream.
    • Command-response CRC errors (open): the same responses are misread identically every time: CMD13 calculated 0x7c vs received 0x7e, CMD17 0xcc vs 0xce, CMD55 0x64 vs 0x66. They always differ in the last CRC7 bit. They appear around clock changes and the CMD6 (High Speed) sequence, at fractional dividers (12.5, 20.8, 25 MHz) and once at 15.625 MHz during CMD6. They never appeared during data tests 4–7 at 15.625 MHz. They look deterministic (a response-sampling or decoding issue in the PIO/driver path) rather than noise. Not yet root-caused. Because of them, the default is 15.625 MHz in default-speed mode and High Speed is not used.
    • The 10 MB/s USB mass-storage target is not reachable at clk_sys 125 MHz with this PIO program (4 PIO cycles per SD clock → 31.25 MHz maximum, High Speed only). Best measured: 6.5 MB/s write, 7.3 MB/s read. Open item, no decision (options: higher clk_sys, a different SDIO PIO program, or accept a slower sync).
    • Leaving High Speed mode needs care: the card is quieted at the current clock (open write closed, not busy), the clock lowered, and only then is the card reset and re-identified, with up to three tries; the sweep test fails if the card cannot be brought back.

    Failure checklist¶

    Symptom Likely cause / action
    Card ignores the first identification after a debugger reset A reset mid-transfer can leave the card in a data state; a power cycle always fixes it. hal_storage_init() makes up to three attempts; before the 2nd and 3rd it sends four CMD12 (stop transmission: no data, harmless to an idle card, ends an open read or write-multiple) at the 400 kHz identification clock, reads each response, waits 50 ms and logs storage: card did not identify, wake-up attempt N. Nothing is written. A missing card still fails in well under a second (about 0.65 s in all, 0.5 s more than with a single attempt); it is called once at boot, never in a loop
    Test 1: NO_CARD or init timeout Card not fully inserted, 3.3 V missing, CLK/CMD/DAT wiring (GP2-GP7), no pull-up on CMD, card not powered
    CRC errors, or tests pass at 12.5 MHz but fail higher Clock too fast for the wiring: lower the clock, shorten wires, check pull-ups on CMD and DAT0-3
    Test 2: NO_FILESYSTEM No FAT/exFAT volume (blank card, unusual partition layout), or the file system configuration is wrong (sector size not 512, exFAT disabled)
    Test 2 slow Free-space scan on a big FAT32 volume is slow by nature; it is printed separately
    Slow random reads (test 6) Small clusters or a fragmented file; compare plain and fast seek
    Streaming misses deadlines Read time varies: look at the worst read time; lower the clock only if errors appear, otherwise raise it
    Test 4 mismatches Bus errors that slipped past the CRC, or a bad card; repeat at a lower clock
    Test 8 stops at 25 MHz / "High Speed switch failed" The card refused High Speed, or a command response failed its CRC (see the open item above); keep the default
    SDIO "Timed out waiting for data block" on large reads The library's 256-block DMA bug: make sure reads go through the HAL's chunked guarded_read
    Card unreadable on a PC after test 9 Check the partition table with a PC tool: one partition, type 07, starting at the allocation-unit boundary; see ADR-0008
    "writes locked until re-init" or "write fault" A write failed or the card status after a write was bad; the card was reset, check wiring and clock
    A test says a file already exists An earlier run was interrupted; delete /neupod-test on a PC and run again
