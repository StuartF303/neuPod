    Waveshare RP2350-Touch-AMOLED-2.41 (dev board)¶

    The product runtime (neupod) also builds for this board, as a second board of the RP2350 platform (-DNEUPOD_BOARD=amoled241; the default, pico2w, is unchanged). It is a dev board: it has an RP2350B with PSRAM and a touch AMOLED, which is the shape of the final board's compute and display, but no radio, no audio and no click wheel.

    scripts/build.sh rp2350-amoled241                                 # -> build/rp2350-amoled241/platforms/rp2350/neupod.uf2
picotool load -f -x build/rp2350-amoled241/platforms/rp2350/neupod.uf2   # a running image reboots into BOOTSEL by itself

    (scripts/build.sh rp2350-amoled241 is cmake -S . -B build/rp2350-amoled241 -G Ninja -DNEUPOD_PLATFORM=rp2350 -DNEUPOD_BOARD=amoled241. NEUPOD_BOARD has to be chosen when the build directory is created, because it selects the SDK's board header: use a separate build directory per board.)

    The console is the USB serial port (CDC; it shows up as /dev/serial/by-id/usb-Raspberry_Pi_Pico_*): the board's UART0 pins are not brought out. UART0 stays enabled as well (the panic path writes to it).

    On a Linux desktop ModemManager probes a new serial port for a minute or so, so a terminal may not be able to open it at once, and the boot lines printed in the meantime are lost; open the port as soon as it opens and press the reset button (or reflash) to see them again. The runtime keeps printing a heartbeat and the audio, UI and Wi-Fi statistics every 10 s.

    Status LED on the CYW43 chip none
    Clock 125 MHz 125 MHz (QSPI SCLK = 62.5 MHz)

    Not built for this board: the display_test, i2c_test and storage_test executables (Pico 2 W bench tools).

    Display notes¶

    • Orientation. The panel's own MADCTL (0x36) is 0xA0 (MY|MV) by default: the controller addresses itself as landscape, with a page (row) offset of 16 (the 450 visible columns sit 16 from one end of the controller's 480-column memory and 14 from the other; the offset has to be the one on the side the mirror bit makes "first", else a 2 px band of unused memory shows on an edge). -DNEUPOD_AMOLED_LANDSCAPE=3 turns the picture by 180 degrees (MADCTL 0x60, offset 14) and the touch mapping with it, so the pair stays consistent. On the owner's bench, MADCTL 0x60 with the touch mapping below (landscape x = raw y, y = 449 - raw x) was 180 degrees apart; the default is therefore the rotated display with that touch mapping. The offsets come from other RM690B0 drivers; whether a band shows on an edge has not been checked by eye by me.
    • Even windows. The controller addresses whole pixel pairs: hal_display_set_window() returns HAL_EINVAL for an odd x, y, width or height. The UI rounds its flush areas outwards (LVGL rounder).
    • Brightness is the panel's own register (0x51): hal_display_backlight() 0..255. hal_display_sleep() sends DISPOFF + SLPIN.
    • The build selects the UI profile 600x450 automatically.

    Touch notes¶

    hal_touch_read() returns the first contact in the display's landscape coordinates (x 0..599, y 0..449). The raw controller values are portrait (x 0..449, y 0..599): landscape x = raw y, landscape y = 449 - raw x. -DNEUPOD_AMOLED_TOUCH_LOG=ON logs every press, a move every 200 ms and the release with raw and mapped values (off by default: a USB terminal that is attached but not reading can block the input task). The chip ID line is always logged at init. The input task initialises the controller (it logs its chip, vendor and firmware IDs) and reads the points under the I2C mutex.

    Storage notes¶

    SDHC and SDXC cards only (the library's SPI mode refuses standard-capacity cards). The SPI clock is 20.8 MHz (125 MHz / 6). There is no SD Status register (so no speed class or allocation unit in the card info), no CMD6 and no bus-clock change in this mode; those HAL calls answer "unsupported". The write guard, mounting, formatting and the music library work as on the Pico 2 W.

    Power notes¶

    The Power key held for 10 s shows the "shutting down" countdown (hal_system_can_poweroff() is true); at the end the runtime lets the card finish its writes and drops BAT_Control. On battery the board then switches off when the key is released. On USB power it cannot: the request is refused and the latch is closed again. After dropping the latch the HAL waits for the key to be released (at most 3 s, in the UI task) and then 0.5 s more; still running means USB power. No VBUS or charger-status line is read (the schematic was not checked for one). The Power key is read as level; the press that switched the board on is not counted.

    What is not done¶

    • PSRAM (8 MB on QMI CS1) is not initialised by the firmware; the driver of the bring-up probe (testbed/amoled241/bringup/src/psram.c) is the starting point.
    • No battery voltage (GPIO40 through the x3 divider) and no RTC / IMU.
    • Display and touch orientation, and brightness, have been checked through the registers and the console only.
