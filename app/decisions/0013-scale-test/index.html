    0013: The scale test and its targets¶

    Status: Accepted (2026-11-26) · Owner: Test engineer · The targets marked "lead call" are proposals for the lead and the owner; the spec's own are marked "spec"

    Context¶

    • The spec (The library): "Sizing target: 20,000 tracks. First scan of 5,000 FLAC files in under five minutes on a mid-range phone; a rescan with no changes in under ten seconds. (Targets are proposals; measure and report.)" Its test table: "A generated 20,000-track library: scan time, memory, scroll smoothness", at the end of the library phase. It sets no target for list reads, the database or memory.
    • The last handoff asked for "real queries" before the scale test: DriftLibraryView reads the whole tracks table and folds it into the firmware's entities in Dart.
    • mobile/tool/gen_test_library already wrote a scale library, but not a real library's shape (200 artists of 10 albums of 10 tracks, FLAC and MP3 only, no compilations).

    Decision¶

    The scale library (scaleCases, --scale N) is shaped like a real one: about 13 tracks an album and 2.5 albums an artist, so 20,000 tracks are 1,500 album folders by 563 album artists; FLAC, MP3 and M4A (ALAC) in turn, one format an album, with real tags written into the repository's small fixtures, so the real tag readers run; a compilation every 15th album (by "Various Artists" or by the flag alone, its tracks by other artists); two discs every 8th other album (disc tags, (Disc n) folders); "The" artists, some in ", The" folders; accented, Nordic, Cyrillic and Japanese names; every 50th track untagged (owner decision 15, so each makes its folder an album: 1,901 albums in the Albums list). 20,000 tracks are 314 MB. The generator gained an M4A tag writer (m4aWithTags), which also fixed the curated library's "untagged" ALAC file: it was the fixture byte for byte, and the fixture has tags.

    The test is mobile/test/scale/library_scale_test.dart (tag scale). It generates the library in a temporary folder, scans it with the app's LocalLibraryScanner (through a dart:io storage root, test/support/host_library.dart) into a database file opened as the app opens it (SQLite in a background isolate), and deletes it all afterwards.

    • Every PR runs it at 2,000 tracks inside flutter test, against tight limits of its own (the last column below): about 5 to 10 times what the slower of the M1 host and the CI runner takes, so a regression of that size fails and CI's own variation does not.
    • The full run is NEUPOD_SCALE_TRACKS=20000 flutter test test/scale from mobile/, or the app workflow's scale_tracks input (gh workflow run app.yml --ref <branch> -f scale_tracks=20000), which uploads the numbers as the scale-report artifact. NEUPOD_SCALE_REPORT=<file> writes them as JSON locally.

    Numbers (2026-11-26)¶

Both are flutter test, debug (JIT): the code's cost on a desktop CPU and SSD, which says little about a phone's storage. M1 ranges are over three runs; CI is one run.

    Every target is met on both. The 20,000-track step took 17 s of CI time and the whole check job 2.5 minutes, well inside its 15-minute timeout (a requested scale run gets 30). The phone numbers come from the device check (PROGRESS, phase 3).

    "Real queries": not now (lead call)¶

    DriftLibraryView does not query each list. It reads the tracks table once (one SELECT joined to its source) and folds it into the firmware's artists, albums and genres in Dart (lib_build.c's index_file, stage_entity, ent_cmp, the walk order), then keeps that until the tracks or sources change. Measured at 20,000:

    • every list once loaded takes 0.02 to 5 ms, 20 to 5,000 times under the 100 ms bar, and no index would help it (no list is a query);
    • the one slow step is the first list after a launch or a scan: 0.43 s, of which 0.19 s is the table read and the rest the fold. It happens once, and in practice before the user opens a list: Home counts the songs at launch and again when a scan ends, which loads the view.

    Per-list SQL would need the firmware's entity keys stored at scan time (the collation keys of the album artist and the album, folded as ent_cmp folds them, and the walk order), a schema version 6 with a scan version bump, so every owner's library is read again once, and SQL that reproduces the firmware's fold exactly. That is the bigger, riskier change, for a cost the user should not see. So the fold stays, and the stored-keys design is the plan if the device check shows the first list over 1 s on the iPhone or the Pixel. No schema change was made, so decision 0008's migration rules and the guard tests are untouched.

    Alternatives¶

    • Measure on a device only. It is the real number, but cannot run on every PR; the host run catches regressions and the device check gives the phone's number.
    • A fixed set of committed scale files. 314 MB in a public repository, and no way to change the shape; generated at test time instead, never committed.
    • Every limit scaled with the size. A list read must stay quick at any size, so only the first scan's limit grows with the track count.
