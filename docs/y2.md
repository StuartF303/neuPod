# Innioasis Y2 platform (`NEUPOD_PLATFORM=y2`)

The same firmware as the host build (FreeRTOS tasks, LVGL UI, boot checks, player, FatFs storage), running as a Linux
process on the Innioasis Y2 testbed (MT6582, armv7 hard-float, stock kernel 3.4.67, our Buildroot glibc rootfs). It is a
testbed target for the UI and the library engine, not a product. Nothing here flashes the Y2: the firmware is copied into
`/opt` over ssh. Background on the device itself is in `testbed/y2/README.md`.

## Where the code is

| Path | What |
| --- | --- |
| `platforms/y2/` | the target: `main.c`, `CMakeLists.txt`, `hal/` |
| `platforms/y2/hal/y2_*.c` | portable logic, also built and unit-tested on the PC: evdev decoding and the wheel mapping (`y2_input`), SD device selection (`y2_sd`), power_supply parsing (`y2_power`), the poweroff and reboot requests (`y2_poweroff`), boot-mode detection (`y2_sysfs`), charging-only mode logic (`y2_charge`) and its screen (`y2_chargeview`: the battery drawing and the screen-on timer), RGB565 to XRGB8888 and the page flipper (`y2_fb`), the wired audio path (`y2_audio`: allow-lists, S16 conversion, ring, DAC state machine) |
| `platforms/y2/hal/hal_*.c` | the HALs that touch the device (display, input, console, storage, battery, audio, radio, i2c, system) |
| `cmake/toolchain-y2.cmake` | the cross toolchain |
| `hal/host/freertos`, `hal/host/hal_core.c` | reused from the host build: the FreeRTOS POSIX port, and core 1 as a native thread |
| `tests/test_y2_*.c` | host unit tests (`ctest -R y2_`) |
| `testbed/y2/scripts/deploy-fw.sh`, `select-ui.sh` | deploy and UI selection |

The layout follows the RP2350 target (`platforms/<name>/` with its own `main.c` and `hal/`), not `hal/host`, because this
target has its own toolchain and device HALs. The host build stays the place where HALs are simulated.

## Build

```
scripts/build.sh y2                      # build/y2/platforms/y2/neupod (and neupod.stripped)
```

The compiler is the Buildroot cross toolchain that built the rootfs, so the C library matches the device exactly. By
default `~/y2-build/out-rootfs/host/bin/arm-buildroot-linux-gnueabihf-gcc`; point somewhere else with
`-DNEUPOD_Y2_TOOLCHAIN_DIR=<dir>` and `-DNEUPOD_Y2_TRIPLE=<triple>` or the environment variables `NEUPOD_Y2_TOOLCHAIN` /
`NEUPOD_Y2_TRIPLE`. The secrets code needs mbed TLS from the Pico SDK (`PICO_SDK_PATH`) as on the other targets.

CI cannot use the Buildroot toolchain, so the `y2` job in `.github/workflows/firmware.yml` cross-builds with the Ubuntu
`gcc-arm-linux-gnueabihf` package (about 20 s of installing) and checks that the result is a 32-bit ARM hard-float
executable. That binary is a compile check; only the Buildroot-built one is deployed. The portable Y2 logic is also
covered by the host job's `ctest`.

## What each HAL does

| HAL | On the Y2 |
| --- | --- |
| Display | `/dev/fb0` (mtkfb, 480x360, three pages, XRGB8888). The HAL keeps an RGB565 shadow frame with the ST7789-style window and cursor, so the UI draws as on every target, and `hal_display_present()` converts only the rows that changed into the next page and flips to it with pan plus put (about 64 fps for full frames measured on the device). Nothing is flipped when nothing was drawn. A previous run can leave the pan offset on another page, so the HAL pans to page 0 when it opens. `hal_display_width()/height()` report 480x360. Brightness is `/sys/class/leds/lcd-backlight/brightness` (0..255); sleep and wake switch the backlight off and on. |
| Input | The wheel and ring buttons are the `mtk-tpd` evdev node, the side keys `mtk-kpd`, found by name under `/sys/class/input`. A wheel detent is one `KEY_DOWN` (clockwise) or `KEY_UP` press; it moves a virtual finger by 4 wheel positions, the same as a console `s` or `w`, so each detent is one list step and the UI's scroll acceleration applies as on the real wheel. Centre (`KEY_ENTER`) keeps its real hold time, Menu is `KEY_BACK`, Prev/Next are `KEY_LEFT`/`KEY_RIGHT`, Play/Pause is `KEY_PLAYPAUSE`. A wheel tick within 150 ms after a Centre, Prev or Next press is dropped (a finger brushing the wheel on its way to the button); Menu and Play do not suppress the wheel, because the usual thing after Menu is to scroll the list that appears. A button pressed and released between two polls (the nodes are read every 8 ms) still gives its press and release, one poll apart. Vol+/Vol- call `player_volume_step()` (one step per press, repeating while held). **Power key** (since [ADR-0020](adr/0020-hold.md); the HAL only reports it as a level, `hal_input_power_key()`, and the UI decides what a press means, see [UI](ui.md#hold)): a **tap** (under 0.4 s) turns the screen off at once (backlight off; with Auto-lock on, Hold turns on) and the next input of any kind wakes it and is not delivered; held **2 s** (it fires at 2 s while still held, once, not on release) it **toggles Hold** (lock / unlock, with a bar from 0.4 s, a confirmation, a haptic click and a lock glyph in the status bar); held on, a **"Powering off in 5"** countdown appears at 5 s (letting go cancels) and at **10 s** it logs `y2: power held, shutting down` and runs the firmware's ordinary clean stop (the same path as SIGTERM: the storage task finishes, card writes are locked, the card is synced and unmounted), then starts `/sbin/poweroff` detached in its own session and exits with status 77, which tells the `S91neupod-fw` respawn wrapper not to restart it at once. The wrapper waits 15 s (`NEUPOD_POWEROFF_WAIT` overrides, for tests); init's stop scripts end it during that wait, and nothing waits on anything else, so there is no double stop. If the system is still up after 15 s the wrapper logs `poweroff did not happen, restarting` and respawns the firmware, so a failed poweroff never leaves a dead screen. If `/sbin/poweroff` cannot be started at all the firmware exits 0 and is respawned. (Before ADR-0020 the HAL itself slept the screen on a short press, swallowed input while asleep except Power and Centre/Menu, and powered off at 2 s. All of that moved to the UI; if the side-key node closes mid-press the held Power press is forgotten and reported as released.) The Y2 has no Hold slide switch (`hal_input_hold_switch()` says none). The command can be replaced with the environment variable `NEUPOD_Y2_POWEROFF` (absolute path, no arguments) or `-DY2_POWEROFF_CMD=...`; host tests use it so they never power off the PC. The nodes are drained every 8 ms. |
| Console keys | `w s` scroll, `e` select, `m` menu, `a d` left/right, `p` play. Read from stdin when it is a terminal or pipe, and from a control FIFO, `/run/neupod.keys` (`NEUPOD_KEYS_FIFO` overrides the path): `ssh root@y2 'echo s > /run/neupod.keys'`. On the FIFO and on piped stdin a newline is ignored, so `echo s` is one scroll step and not also Select. A stdin that is `/dev/null` or ends is dropped; the process keeps running. |
| Storage | The microSD as a raw block device under FatFs, the same layering as the Pico (see below). |
| Charging-only mode | When the Y2 is "off" with USB attached, stock LK boots the kernel again in power-off-charging mode: `/proc/cmdline` shows `boot_reason=1` (BR_USB) and `/sys/class/BOOT/BOOT/boot/boot_mode` reads 8 (KERNEL_POWER_OFF_CHARGING) or 9 (LOW_POWER_OFF_CHARGING). `main()` reads that file first (before any HAL init) and logs `y2: boot_mode N (charging|normal)`; an absent, empty or unreadable file counts as a normal boot. In mode 8 or 9 the firmware starts no UI, storage, audio or FreeRTOS and runs `y2_charging_main()` (`platforms/y2/charging.c`): framebuffer mapped once and cleared, then a 250 ms sleep loop (idles near 0 % CPU) reading the `mtk-kpd` (side keys) and `mtk-tpd` (wheel) nodes. **Screen**: for 10 s after entering the mode, and again after every key press or wheel touch, the backlight is on (brightness 255) and an own-artwork animated battery is drawn straight into the framebuffer (`y2_chargeview.c`, no LVGL: dark theme colours, 5 segments that fill one by one up to the current level, hold one step and start again every 600 ms; green, red at 15 % or less; the percentage and CHARGING below). The gauge saying Full or Not charging with the charger present shows a still full battery captioned CHARGED. No gauge reading shows an empty battery and `--%`. While Power is held an amber HOLD TO RESTART caption and a bar fill over the 2 s. After the 10 s the backlight goes to 0 and nothing is read or drawn until the next key. Only the backlight node and `/dev/fb0` are written. The picture is size-independent (the panel is 480x360; the tests draw 320x240 as well, `ctest -R y2_chargeview`, snapshots in `build/host/snapshots_charging`). **Power held 2 s** (this mode has its own loop and timer, `y2_charge`; the 10 s player gesture does not apply): logs, spawns `/sbin/reboot` detached (override `NEUPOD_Y2_REBOOT` or `-DY2_REBOOT_CMD=...`) once per press and exits 77, so `S91neupod-fw` does not respawn at once (the 15 s "still up, restarting" fallback applies as in normal mode). **Charger removed**: every `/sys/class/power_supply/*` that is not the battery is read (`online`; every non-battery supply, on the device `ac`, `usb` and `wireless`; any one online counts; a missing or non-0/1 value counts as unreadable); after it has been continuously offline for 3 s (any online reading restarts the timer) it spawns `/sbin/poweroff` and exits 77. The 3 s timer is only armed once an online reading has been seen since the loop started (the charger can read 0 early in a charger boot); a charger that never reads online leaves the device up. If no charger supply can be read the state is "unknown" and never powers off. A **short Power press** only wakes the screen. SIGTERM exits 0 (the wrapper would respawn it, but init stop kills the whole group first). If a command cannot be started it is logged and retried (next hold, or after another 3 s offline). `S90neupod-demo` skips itself in boot mode 8 or 9 when `/opt/neupod-fw/neupod` is executable (on a demo-only device it behaves as before); command line arguments such as `--run-ms` are ignored in charging mode and logged as such. `S91neupod-fw` starts the firmware in that mode whatever `/etc/neupod-ui` says; both read the mode from `NEUPOD_BOOT_MODE_FILE` (default the sysfs path) so they can be tested in a sandbox. `select-ui.sh demo` run while the device is in charging-only mode will not start the demo (and will roll back). Not tried on the device yet: the picture, its timing and the backlight on/off have only been checked on the PC (rendering and timer tests, snapshots); the loop, the Power hold and the unplug path are unit-tested (`y2_charge`, `y2_sysfs`) and the init-script logic was run in a sandbox with fake sysfs and binaries; on the bench, `reboot` from this mode with USB attached came back with boot_mode=0 and boot_reason=4, a normal boot, so there is no charging loop (real power_supply nodes: ac, battery, usb, wireless; usb/online=1 when plugged). |
| Battery | `/sys/class/power_supply/battery`: `capacity`, `batt_vol` (mV; `voltage_now` in microvolts is also accepted) and `status`. There is no charge-rate reading, so while charging or discharging the rate is a fixed plus or minus 10 %/h, which is what makes the UI show "charging" or "discharging". Gauge-chip calls (alert threshold, hibernate, reset) answer "not supported". |
| Audio | **Wired headphones**: the CS43131 DAC behind the MT6582's audio unit, through `/dev/cs43131_dac` and `/dev/eac` (`hal_audio.c`; the logic, with its safety allow-lists and state machine, is `y2_audio.c`, host test `y2_audio`). Used only while `/sys/class/switch/h2w` reports headphones (state 1 or 2; the DAC driver does the detect), 44.1 kHz / 16 bit only (other rates are resampled or refused as for any fixed-rate sink), and the backend is `cs43131` when both nodes open, which is what makes the boot check pass; otherwise it is a timed null sink (no speaker on the Y2) and the check says audio is degraded. The audio core's 32-bit blocks go through a lock-free ring (4096 frames) to a plain pthread that does blocking `write()` on `/dev/eac`, so the DAC's own clock paces the player (the block clock waits for room in the ring instead of a timer); that thread never calls the RTOS. 32 to 16 bit is rounded with TPDF dither whenever bits below the 16th are set (any volume below 0 dB), bit-exact otherwise. **Volume**: the CS43131's hardware index is fixed at 11 (register 0x29, -20.5 dB, about 0.2 Vrms at full scale) and the user volume stays the software volume (2 dB steps, -30 dB at power-up); `NEUPOD_Y2_DAC_INDEX=n` in `/etc/neupod-fw.env` overrides it (0 to 11, clamped; unparseable = 11). **Clicks**: the DAC is powered (0x4302, stereo 0x4307) by the first audible block, not at boot, and stays on across tracks and pauses; its volume is set to mute (index 0, the kernel applies it 80 ms later) before the stream is torn down or the DAC powered down and restored after the stream is running, followed by 100 ms of silence before the audio. Digital silence for 3 s stops the AFE stream (DAC stays on); 30 s after that the DAC is powered down (0x4303); a clean stop does it too. Headphones pulled out: stream and DAC stopped at once (within the 200 ms jack poll), and while playing on the wired output the audio route pauses with the banner `Headphones unplugged` (plugging back in does not resume). Output routing is unchanged: Auto uses Bluetooth while a headset stream is open (the DAC is left alone), else wired. A device error falls back to the null sink for 5 s, then retries. Only whitelisted AFE offsets (0x10, 0x14, 0x20, 0x4c, 0x3a0, 0x3ac, 0x4c4) and device commands are ever issued: never the PMIC registers, the speaker amplifier, the CS43131 mono path, init or debug register file. Log lines: `audio: DAC on`, `stream started`, `stream stopped after 3 s of silence`, `DAC powered down`, and every 10 s while streaming `underruns=... write_us avg/max=...`. |
| Radio | Bluetooth only (docs/bluetooth.md): BTstack over the combo chip's `/dev/stpbt` on a thread of its own, started by `hal_bt_init()`. `hal_system_late_init()` reports the radio present only if `/data/BT_Addr` is a valid address and `/dev/stpbt` opens (the init script `S80mtk-bt` makes that so; without `/opt/mtk-wmt` staged it does nothing and Bluetooth is greyed out). Wi-Fi is not present: the boot check marks it unavailable and the `hal_wifi_*` calls answer "no device". |
| Haptics | The ERM motor behind `/sys/class/timed_output/vibrator/enable` (writing N switches it on for N ms), through `platforms/y2/hal/hal_haptic.c`, which implements `hal_haptic.h` in place of the DRV2605L driver (no I2C is faked; `hal_i2c` stays a stub). The boot check opens the node for writing and logs `haptics: timed_output vibrator (ERM)`; if it is missing or not writable the check reports haptics unavailable as `timed_output vibrator: no response` (and the full reason on the console). The app's click (one per wheel detent, the ERM click effect 3) is a **tick**. Calls come from the app's haptic task, never from the input or UI path (the UI only drops a byte in a non-blocking queue), and each pulse is one short write opened with `O_CLOEXEC`. A rest of 45 ms after each pulse (on top of the task's 35 ms request gap) coalesces a fast scroll into separate taps, not a continuous buzz. Pulse lengths, one table: tick 15 ms, click 30 ms, strong 60 ms (DRV2605 ROM ids 3, 6, 9, 12, 24-26 are ticks; 1, 4, 10, 14 strong; the rest clicks). An ERM needs time to spin up, so very short pulses may not be felt: tune on the bench with `NEUPOD_Y2_HAPTIC_MS="tick,click,strong"` (decimal ms, 1 to 500; an empty field keeps its default, e.g. `20,,80`; a fourth field, even a blank one, counts as bad; bad fields are ignored and logged). On the device write it to `/etc/neupod-fw.env`, then run `/etc/init.d/S91neupod-fw restart`, for example `echo 'NEUPOD_Y2_HAPTIC_MS="20,40,90"' > /etc/neupod-fw.env` (the same file carries `NEUPOD_Y2_POWEROFF` and `NEUPOD_Y2_REBOOT`). `S91neupod-fw` sources it before starting the app, only if it is a regular file (not a symlink) owned by root, not writable by group or others and valid shell; otherwise it logs that it was ignored. The file is optional and `deploy-fw.sh` never creates or overwrites it. Calibration, actuator choice, LRA, sequences and RTP are not supported (`HAL_ENOTSUP`); the actuator reads as ERM, open loop, so Settings shows calibration as not needed. Host test: `y2_haptic`. |
| Stopping | SIGTERM (or SIGINT) only sets a flag. The monitor sees it within 100 ms, waits up to 2 s for the storage task to go idle (no queued request, no settings write in flight), locks card writes (fsync, back to read-only), unmounts and exits with status 0. Settings that were changed less than a few seconds before the stop and not yet saved are not forced out. |
| Time | Monotonic clock only; the device's wall clock is wrong and nothing depends on it. The chip ID that binds the secrets file is a hash of the eMMC's CID read from the MMC host's sysfs entry. |

### Wired audio: bench steps

Not yet heard in the firmware (the tone tool proved the device sequence). With headphones in: boot log shows `audio: CS43131 wired output available`
and `boot: audio ok`; play a 44.1 kHz track: `audio: DAC on`, `stream started`, sound after about 0.3 s, no clicks between tracks, `underruns=0` in
the 10 s lines (a few at start-up are the ring filling). Pause 4 s: `stream stopped after 3 s of silence`; Play again: sound resumes, no `DAC on`
(the DAC stayed powered). Pause 35 s: `DAC powered down`. Pull the headphones while playing: sound stops, the player pauses, banner `Headphones
unplugged`, log `audio: headphones unplugged`. Too loud or quiet at the default: set `NEUPOD_Y2_DAC_INDEX` (lower is quieter, 11 at most) in
`/etc/neupod-fw.env` and restart the firmware. A 48 kHz track is resampled or refused by the player, never played at the wrong speed.

### Storage and the card rule

`hal_storage` reads and writes with `pread`/`pwrite` at sector offsets, under the same write lock as everywhere. The device is
open `O_RDONLY` while writes are locked; unlocking writes reopens it `O_RDWR | O_SYNC` (validated again first), and locking them
again fsyncs and goes back to read-only. All descriptor changes are under one lock (taken with try-lock and a scheduler sleep:
a blocking native lock could starve a preempted lower-priority task under the FreeRTOS POSIX port). It opens the whole card, usually `/dev/mmcblk1`, and
FatFs finds the partition from the MBR exactly as on the Pico; it uses partition 1 (`/dev/mmcblk1p1`) only if the whole-disk node is
missing. A write-protected card is opened read-only and writes report write-protect. Formatting is not offered on the Y2.

**Hard rule: the firmware never opens `mmcblk0` or any of its partitions** (the internal eMMC with the boot chain and the
rootfs). `y2_sd_pick()` scans `/sys/block` and accepts a disk only when all of these hold:

- the name is `mmcblk<N>` (or `mmcblk<N>p<M>` for a partition) with N at least 1, digits only and no leading zeros, so `mmcblk0*`,
  `mmcblk0boot0`, `mmcblk1boot0` and `mmcblk01` are refused by name whatever sysfs says;
- `/sys/block/<disk>/device/type` reads exactly `SD`;
- its controller is not `mmc0`. The host comes from where `/sys/block/<disk>` really resolves (the `mmc_host/mmc<X>` part of the
  path); if that cannot be worked out the disk is refused (fail closed). On the device the eMMC was observed on `mmc0` and the SD slot as `mmcblk1` under `mmc_host/mmc1` (2026-11-11).

The `removable` attribute is ignored: the MTK slot driver reports `0` for the real SD slot, so it says nothing useful (this
replaced an earlier rule that refused the card with `mmcblk1 is type SD but not removable`). The card is found under whichever
`mmcblk<N>` it enumerates as, not only `mmcblk1`; if more than one disk qualifies the lowest N is used and the log says
`storage: <n> SD disks qualify, using the lowest`. `hal_storage.c` checks the name again right before `open()` and `lstat()`s the node first: it must be a real block
device (not a symlink; the open also uses `O_NOFOLLOW`), its major:minor must equal the one in sysfs, and neither may be
the eMMC's device numbers (`/sys/block/mmcblk0/dev` and its minor range, or 179:0 to 179:7 if that is unreadable). The opened
descriptor is checked the same way. Every reopen (read-only to read-write) repeats all of it and also requires the same
card (see below).
Anything else is refused and logged, and the firmware runs without a card: fail closed. The selection is unit-tested against a
fake sysfs tree with the real symlink layout (`tests/test_y2_sd.c`).

While a card is held, "card present" means that same disk is still there and is the same card: its sysfs device numbers,
`device/cid` and name, serial, manufacturer, OEM and date are remembered at open. A card pulled and re-inserted between two
polls (even under a new node, or a different card behind the same one) is treated as a removal followed by an insertion:
the descriptor is dropped, storage goes degraded and the next poll opens the new card. Re-inserting the very same card
with identical identity within one poll is indistinguishable from it never leaving; the old descriptor then fails with
`ENODEV`/`ENOMEDIUM` and is dropped.

The rescue init (`testbed/y2/rescue/overlay/init`, line 186) and `diag.sh` (line 99) still hard-code `mmcblk1`; that is fine
for the rescue tools, which are separate from the firmware and do not use its card rule.

The device identity (`hal_chip_id`) is unrelated: it hashes the read-only eMMC CID attribute
`/sys/class/mmc_host/mmc0/mmc0:0001/cid` and does not take part in card selection.

No card is the normal state at boot: the log says `storage: no mmcblk1 or higher (no card inserted)`, Settings and Files say so, and
settings stay in RAM for the session. With `storage_hotplug` set in `main.c`, the monitor looks for a card every two seconds
while storage is unavailable; when the card disk appears (mdev creates the node) the storage boot check runs again and, if the
card mounts, storage turns available and the settings load. A card that fails the check (no filesystem, unreadable) is not
retried until it has been taken out and put back; a failed check closes the device and reports why ("no filesystem", "card
unreadable"). While a card is in use the same poll watches the slot: if it disappears (or reads fail with EIO and the sysfs entry
is gone) storage turns degraded, settings go back to RAM-only, and putting the card back runs the check again. The boot check
and the retry never run at the same time, and a retry never starts while a settings write is in flight. Nothing in the rootfs mounts the card and the firmware does not either: it
reads the filesystem itself.

## Running it

`deploy-fw.sh` and `select-ui.sh` (in `testbed/y2/scripts`) do the work; see `testbed/y2/README.md`. On the device:

| | |
| --- | --- |
| Binary | `/opt/neupod-fw/neupod` (flags: `--splash-hold-ms N`, `--run-ms N`, `--script "s s e ..."`) |
| Init script | `/etc/init.d/S91neupod-fw`, a respawn wrapper (2 s pause), log `/tmp/neupod-fw.log` on tmpfs, emptied when it passes 256 KB, PID files `/run/neupod-fw.pid` and `/run/neupod-fw.app.pid`; stop kills by PID only |
| UI selection | `/etc/neupod-ui` holds `fw` or `demo`. `S90neupod-demo` (the .NET demo) and `S91neupod-fw` each start only if selected, because both draw on `/dev/fb0`; a missing file means `demo` |

To look at the screen, read the visible page back from the framebuffer: the pan offset is in
`/sys/class/graphics/fb0/pan` (`x,y`), and 360 rows of 1920 bytes from that row offset in `/dev/fb0` are the picture
(XRGB8888 little endian).

## What is measured and what is not

Measured on the device (kernel 3.4.67, firmware running; measured before the 480x360 UI profile, when a 320x240 UI was drawn in the top-left corner): boots clean with no card; idle CPU 5.2 % of one core over 30 s (9.6 % with the port's default 1 kHz tick, and 105 % before the idle hook, because the
port's idle task otherwise spins). The Y2 uses a 250 Hz tick (4 ms; delays round up to
whole ticks, so `os_tick_ms()` has 4 ms resolution on this target only) because the port's tick is a signal plus a context switch (1000 of them a second were about half of the idle CPU); resident memory
about 1.6 MB (4 MB FreeRTOS heap, almost all untouched); page flips up to 64 fps; the UI driven through the FIFO (scroll,
select, back) including the Files screen's "no card" message and the test tone playing on the null sink.

Not verified yet: the physical wheel, ring buttons and side keys on the real hardware (the decoding and mapping are unit-tested
with captured codes, but no event was injected on the device), the Vol keys, the card path with a real microSD (everything but
the final open is unit-tested; the hot-plug re-check has not run on the device), and charging-only mode and the power key (screen sleep and hold-to-power-off are unit-tested but have not been tried on the device). The UI now uses the 480x360 profile
filling the whole panel (log: `ui: profile 480x360 on 480x360 panel`) with the 192 KB LVGL pool of hosted builds; the numbers above have not been re-measured with it.
