# Audio output (I2S, test signals, WAV, FLAC, MP3, ALAC)

Phase 1 sound comes out of the Pimoroni Pico Audio Pack ("the Audio Pack DAC") over I2S, driven by the PIO and
DMA from the bare-metal audio core ([ADR-0011](adr/0011-bare-metal-audio-core.md), [Runtime](runtime.md)).
The audio policy is [ADR-0003](adr/0003-audio-quality-policy.md): decode once to a 32-bit mixer, no
resampling; the sink is re-clocked per file instead.

## Pins

| Signal | GPIO | Notes |
| --- | --- | --- |
| I2S DATA | GP9 | PIO0 `out` pin |
| I2S BCK | GP10 | PIO0 side-set bit 0 |
| I2S LRCK | GP11 | PIO0 side-set bit 1 (BCK and LRCK must be consecutive) |
| Mute / amp enable | GP22 | plain GPIO, driven by core 1 (and by core 0 at boot and in the fatal-error path) |

The Audio Pack is a TI **PCM5100A** DAC with a **PAM8908** headphone amp behind the "phones" jack (low/high gain
switch); "line out" is the DAC output directly. Try both jacks.

No MCLK: the PCM5100A runs its internal PLL from BCK, which must be 32, 48 or 64 × fs with a 50 % LRCK. Our 32-bit
slots give 64 fs. SCK is tied low on the Pack; the format pin is hardwired to standard I2S (one-BCK delay), which is
what `neupod_i2s.pio` produces.

## Resource allocation

| Resource | Used by | Notes |
| --- | --- | --- |
| PIO0, 1 state machine, 8 instructions | I2S transmitter (`platforms/rp2350/hal/neupod_i2s.pio`) | claimed with `pio_claim_unused_sm`, program added and removed at open/close. pio1 = SD (carlk3), pio2 = CYW43 + click wheel |
| 2 DMA channels (claimed dynamically) | ping-pong, chained A to B to A, 512 words each (256 stereo frames) | high bus priority; read pointer wraps inside its 2 KB buffer (ring), so a late restart replays the old block instead of reading past the buffer |
| `DMA_IRQ_1`, enabled on **core 1** | block-complete interrupt, refills the finished buffer | `DMA_IRQ_0` stays with the SD library on core 0 |
| 2 x 2 KB DMA buffers, 32 KB PCM ring, 32 KB data ring | RAM | PCM ring size is `NEUPOD_PCM_RING_FRAMES` in `app/os/memory_budget.h`; data ring in `audio_shared.c` |
| Hot path in RAM | `dma_isr`, `on_block`, `audio_apply_gain`, the ring functions, `hal_audio_write`, `hal_audio_mute` | `NEUPOD_RAM_FUNC` / `__not_in_flash_func` |

The sink is chosen at build time: `scripts/build.sh rp2350 -- -DNEUPOD_AUDIO_SINK=i2s` (default) or `null`
(the old discard-on-a-clock sink, touches no pins). The host build uses SDL for audible output when SDL2 and an
audio device exist (`NEUPOD_HOST_AUDIO=0` forces silence), otherwise it is the null sink.

### Interrupt flow

1. Start: both buffers hold silence; DMA channel A is started, the PIO is enabled.
2. When a channel finishes it chains to the other one and raises `DMA_IRQ_1`.
3. The handler acknowledges, then for the finished buffer calls the block callback (`on_block` in
   `app/audio/audio_core.c`), which reads 256 frames from the PCM ring, applies volume, writes them into the
   buffer through `hal_audio_write`. The handler re-arms that channel's count.
4. Ring empty: that block is silence and `underruns` counts it. If the interrupt runs so late that both buffers
   finished, `dma_underruns` (`sink_missed`) counts it and the old block is replayed once.
5. 32 starved blocks in a row (186 ms) while playing: playback stops, the output is muted and the event
   `STORM` is logged.

## Clocking and rate accuracy

The PIO runs at 128 x Fs: two PIO cycles per BCK, 64 BCK per frame (32-bit slots). The divider comes from
`clk_sys` = 125 MHz in 1/256 steps (16.8 fixed point), rounded to nearest.

| Fs | divider | achieved Fs | error | BCK | PIO cycle |
| --- | --- | --- | --- | --- | --- |
| 44.1 kHz | 22 + 37/256 | 44099.488 Hz | -11.6 ppm | 2.8224 MHz | 177 ns |
| 48 kHz | 20 + 88/256 | 48003.072 Hz | +64 ppm | 3.0722 MHz | 163 ns |
| 88.2 kHz | 11 + 18/256 | 88214.538 Hz | +165 ppm | 5.6457 MHz | 89 ns |
| 96 kHz | 10 + 44/256 | 96006.144 Hz | +64 ppm | 6.1444 MHz | 81 ns |

The monitor line `audio sink:` prints the actual rate and divider read back from the hardware setup.
Consequences:

* The DAC slaves to BCK, so a rate error is not a sync problem; it only changes pitch and duration, by at most
  165 ppm (0.29 cent; a 4-minute track is 40 ms shorter or longer). Not audible.
* The fractional divider dithers each PIO cycle between 22 and 23 system clocks (and so on), so a BCK edge moves by at most
  one system clock, 8 ns, around its ideal place: 2 % of a 354 ns BCK period at 44.1 kHz, 5 % at 96 kHz. A DAC that
  regenerates its clock with a PLL (as no-MCLK DACs do) filters this. Not measured on the board; an oscilloscope on GP10 would show it.
* 88.2 and 96 kHz are generated by the same code and accepted by the WAV player, but were not run on hardware.

## Mute line (GP22)

* **GP22 drives the PCM5100A's XSMT pin (TSSOP-20 pin 17), active LOW**: low = soft-muted, high = playing
  (design response, 3 Nov 2026, from the Pack schematic; confirmed on the bench the same day). The build default
  `NEUPOD_AUDIO_UNMUTE_LEVEL=1` is correct.
* The DAC also **auto-mutes on a clock error**: BCK and LRCK must be running continuously, and its PLL locked,
  before XSMT goes high.
* **Current behaviour (as built):** muted from boot (`hal_system_init`), at sink open and close, on stop, on an
  underrun storm and in the fatal-error path (`hal_panic` → `hal_audio_force_mute()`, which also aborts the DMA and
  stops the PIO). The audio core opens XSMT one block before a fade-in and closes it after two silent blocks
  (`app/audio/audio_core.c`), and `hal_audio_close()` stops the I2S clocks between streams. So XSMT toggles with every
  start/stop. The stream is opened at boot and its clocks keep running, so in practice XSMT rises long after the PLL has locked.
* **Bench, 3 Nov 2026: works.** 1 kHz test tone heard on the "line out" jack (DAC direct, no PAM8908) at -30 dB. The earlier silence was wiring:
  the GP9 (DATA) and GP22 (XSMT) jumpers were on the wrong Pico pins. Register read-back over SWD (SIO_IN / IO_BANK0
  STATUS) showed both pins driven correctly while the Pack end read 0 V, which is how it was found.
* **Design recommendation (optional, not built):** raise XSMT once after the clocks have settled and leave it high,
  doing start/stop/pause with the gain ramp only; XSMT low only for force-mute (panic, storm) and sink close. Not needed
  for function on the testbed; it reduces DAC soft-mute ramps at track boundaries.

## Volume safety

* Volume is **attenuation in whole dB**, applied in the 32-bit domain. Start-up level is **-30 dB** and is
  sent to the audio core before anything can play; the audio core also boots at -30 dB by itself. The volume is saved on the card
  (settings store, [Bluetooth](bluetooth.md)) and restored at boot, but **never louder than -30 dB**: a saved louder level comes back as -30 dB.
  Approved replacement (not built): see [Volume restore policy](bluetooth.md#volume-restore-policy).
* The UI steps 2 dB per wheel click. The engine never applies gain above 0 dB, and a build-time hard cap
  (`NEUPOD_AUDIO_VOLUME_CAP_DB`, default 0, meaning full scale allowed) sets the loudest level; raise it for a
  headphone-safe build. At 80 dB or more the output is silent.
* The test tone is -20 dBFS; with the default volume it reaches the DAC at -50 dBFS peak. The Test tone screen
  prints that figure. Leaving the Test tone screen stops the sound.
* Volume changes, pause, resume, start and stop are ramped linearly across one 5.8 ms block (no clicks).

## Bit-perfect note

PCM files are converted to 32 bits exactly (16-bit `<< 16`, 24-bit `<< 8`, 32-bit as is; mono duplicated to both
channels), with no dither and no resampling. At **0 dB volume** the samples then go to the DAC unchanged
(verified by the unit tests; the gain stage is skipped). **Only 0 dB is bit-perfect**: any other setting
multiplies the samples. The first and last block of a start/stop/pause are ramped even at 0 dB. The DAC itself
and its analogue stage are not "bit-perfect" in any measurable sense; the claim is about the digital path.
The Audio Pack DAC takes 32-bit slots; how many of the bits it uses is the DAC's business.

## Test signals and WAV

| Source | What | Notes |
| --- | --- | --- |
| 1 kHz tone | sine, -20 dBFS peak, both channels | phase accumulator, 1024-point table with linear interpolation (worst error about -104 dBFS) |
| L/R ident | the same tone, 1 s left only, then 1 s right only, repeating | switches at a zero crossing; if you hear it in the wrong ear the channel order is swapped (slot order is left first) |
| Scale | C4 D4 E4 F4 G4 A4 B4 C5, then B4 down to C4, 300 ms per note, 10 ms raised-cosine attack and release, 600 ms rest, loops until stopped | equal temperament, A4 = 440 Hz; frequencies rounded to a millihertz, phase step exact to 2^-32 |
| WAV | integer PCM 16/24/32-bit, mono or stereo, 44.1/48/88.2/96 kHz | RIFF parser walks the chunks (LIST and other chunks before `data`, odd sizes, extensible PCM); float, 8-bit, other rates and RF64 are rejected with a message |

A different sample rate re-clocks the sink (close and reopen, a few ms) with no resampling. The tones run at the
sink's current rate (44.1 kHz after boot, or the last file's rate).
The storage task reads the card in 2 KB steps into a 32 KB ring (85 ms at 32-bit stereo 48 kHz). End of file
raises an end-of-track event after the last sample has played, then the output ramps down and mutes.

## Codecs: FLAC, MP3, ALAC (and WAV)

| Format | Decoder | Licence | Runs on | Output |
| --- | --- | --- | --- | --- |
| FLAC (16/20/24/32-bit, mono/stereo, 44.1/48/88.2/96 kHz) | `dr_flac` (single header, `app/third_party/dr_libs/`) | public domain / MIT-0 | **core 1** | exact: the sample is shifted left-justified into 32 bits |
| MP3 (MPEG-1/2 Layer III, 44.1/48 kHz) | `dr_mp3` (contains minimp3) | public domain / MIT-0 (minimp3 CC0) | core 1 | float, rounded to nearest and clipped to 32 bits |
| ALAC in `.m4a` (16/20/24-bit; 32-bit rejected, mono/stereo, 44.1 to 96 kHz) | Apple's ALAC decoder core (`app/third_party/alac/`) with a C wrapper (`alac_dec.c`) | Apache-2.0 (see the repository's `LICENSE.md`: no NOTICE file upstream; the C port is marked as modified) | core 1 | exact |
| AAC in `.m4a` | none yet | n/a | n/a | the player says "AAC not supported yet" |
| WAV | our own parser (`wav.c`), raw PCM passthrough | MPL-2.0 | conversion on core 1 | exact |

`dr_wav` is vendored with the others as requested but is not compiled: the WAV path has no codec in it, only a header parser that
we already have and test, so `dr_wav` would add code without adding capability.
More than 2 channels are rejected with a message, as are unsupported rates ("Unsupported sample rate"); mono is played on both sides.

### Where things run

* **Core 0 (storage task)** reads the file, parses the header and tags, and streams bytes through the 32 KB data ring:
    * FLAC: a synthesised 42-byte header (`fLaC` + one STREAMINFO block) followed by the audio frames, so the decoder never has to
      stream through the file's pictures and comments. Tags (Vorbis comments) are read here.
    * MP3: the compressed bytes from the first frame header on (ID3v2 skipped and parsed here; duration from the Xing/Info frame count,
      otherwise estimated from the file size, which can be far off for VBR files that lack one; shown with a `~`).
    * M4A: the container is demuxed here (it needs random access to `moov`): `app/audio/mp4.c` reads `stsd` (the ALAC magic cookie), `stsz`, `stsc`,
      `stco`/`co64`, `mdhd` and the `ilst` tags, and sends each packet with a 4-byte big-endian length in front. The demuxer is codec independent so
      AAC can use it later.
* **Core 1** decodes. The main loop calls the decoder for up to two 256-frame blocks per pass while the PCM ring has room; the block interrupt is
  unchanged and still preempts it. Everything the decoders allocate comes from one static **arena of 116 KB** (`codec.h`), reset at every new stream:
  `malloc` is never called (the vendored allocation macros point at the arena), asserts are compiled out, and there is no stdio.
  `tools/check_core1_closure.py` (Python is required by the RP2350 build; ctest also runs the checker against a known-good and a known-bad fixture, so it is proven able to fail) runs after every RP2350 build and fails it if anything reachable from the audio core's entry points
  could reach the RTOS, stdio, the heap, blocking SDK calls or the panic path (it walks the call graph of the linked image, following branches and every function address found in literal pools; a function whose address is only ever computed would be missed, see the limits in the script's header); the
  `audio_core_rules` token scan still covers our own sources. Core 1's stack is now a 16 KB array of our own (minimp3 alone keeps about 10 KB of scratch on the stack).
* Waiting for data: the decoder's read callback blocks until the bytes are there (core 0 refills at about 2 MB/s). While it waits it keeps handling
  commands: volume, pause and the end-of-stream marker immediately; anything that tears the stream down (stop, a new track, a tone) is parked, the read is abandoned and the command runs
  next, so nothing can deadlock. 32 starved blocks in a row still stops and mutes the output.
* The first block of audio is not played until about 23 ms are buffered (and a stream is complete if it is shorter), so a slow start is silence rather than an underrun.
* **Seeking** (not exposed in the UI yet): forward seeks inside the decoder (including dr_flac's own) discard bytes; an absolute seek backwards sends core 0 a
  request (byte offset), core 0 repositions the file and acknowledges, core 1 then empties the data ring and acknowledges back, and only then does core 0 write again
  (`stream_io.h`; unit-tested with a real second thread).

### Memory and CPU

| | Value |
| --- | --- |
| Arena | 99 KB (101,376 bytes, `CODEC_ARENA_BYTES`). Measured high water: FLAC 4096-sample blocks 35 KB; MP3 57 to 68 KB; ALAC 16-bit 82,072 B, 24-bit 98,456 B. Computed worst cases (`arena_worst_cases_fit`): FLAC at the 8192-sample limit (4096 for 32-bit FLAC, which dr_flac stores at 8 bytes a sample) 72,128 B, MP3 56,984 B, ALAC 24-bit stereo 4096 frames 98,472 B. The monitor prints, every 10 s, `audio decoder: codec=... decode_us_per_256_frames avg/max=.../... load=..% of a core ... arena_high_water=...`. The
figure is the time the decoder spent per 256 output frames with the block interrupt's own time subtracted, its worst single call, and the average as a share of
the 5.8 ms block period (at 44.1 kHz). The ALAC hot loops already run from RAM.

### Metadata

FLAC Vorbis comments (TITLE, ARTIST, ALBUM, TRACKNUMBER), ID3v2.2/2.3/2.4 text frames (TIT2, TPE1, TALB, TRCK; ISO-8859-1, UTF-16 and UTF-8), and MP4 `ilst`
(`©nam`, `©ART`, `©alb`, `trkn`) are parsed on core 0 and shown on Now Playing with the format badge (`FLAC 24/96`, `MP3 320k` or `MP3 VBR ~192k`, `ALAC 16/44.1`) and the
elapsed and remaining time. The screen font has no accented letters, so those show as an empty box. Embedded art is not read yet.

### FLAC verify mode (check without listening)

In Extras > Files, press **Right** on a `.flac` (Select plays it). The decoder runs flat out with no sound, hashes every decoded sample the way FLAC defines its checksum
(each sample as `ceil(bits/8)` little-endian bytes, channels interleaved) and compares it with the MD5 in the file's STREAMINFO at the end of the file.
Now Playing shows `MD5 OK`, `MD5 MISMATCH` or `No MD5 stored in this file`, and the UART prints `verify: '<name>' MD5 OK`. A mismatch means the data from the card or the decoder is wrong, so it tests the whole path
from the card to the decoder. (An MD5 of all zeros means the encoder did not compute one.)

### Robustness

Files are untrusted input. The header parsers bound every length and walk (box sizes are compared without wrapping, a box budget of 20,000, vendor and
comment lengths checked, text conversion never writes past its buffer); ALAC rejects a partial-frame sample count above its frame length (the original
decoder trusted it); an MP4 packet outside the file or larger than the decoder's frame buffer ends the stream; a decode that ends short of the
announced length is an error ("File is truncated or damaged"), so a damaged FLAC can never report `MD5 OK` or `Finished`; and a codec error makes core 0 stop reading the card.
Once a command has interrupted the decoder's wait, every further read fails until the engine has handled it. Core 1's stack has a hardware limit
(MSPLIM) 256 bytes above its bottom, so an overflow faults instead of corrupting RAM. The tests truncate every vector at each early byte and at 40 further
points and flip random bits (fixed seed) in all of FLAC, MP3 and M4A; `-DNEUPOD_HOST_ASAN=ON` adds `test_codecs_asan`, the same tests under AddressSanitizer
and UBSan (signed-overflow and shift reports are switched off: the vendored decoders wrap on corrupt data, which is harmless on ARM).

### Test vectors

`tests/assets/audio/` holds small FLAC, MP3 and M4A files with the MD5 of their source samples, made by `tools/gen_audio_vectors.py` (libsndfile via `uv run --no-project --with soundfile --with numpy`) and
`tools/gen_alac_vectors.py` (Apple's reference ALAC encoder built from `tests/tools/alac_encoder/` with `g++`, plus a hand-written MP4 muxer). `ctest` decodes every vector and compares it bit for bit (FLAC 16-bit 44.1 kHz,
24-bit 96 kHz and 48 kHz, mono; ALAC 16-bit, 24-bit with `co64`, mono), checks the MP3's length and level, the demuxer's sample-table maths, the tag parsers, MD5 against the RFC 1321 vectors,
the arena (including the worst-case sizes) and the core 0 / core 1 stream handshake.

## How to test (bench)

1. Plug the Audio Pack, **headphones off your head** (or very low volume). Flash `neupod.elf`
   (`scripts/build.sh rp2350`, then `scripts/flash.sh`). The splash shows the audio icon solid
   if the PIO and DMA stream started (the DAC cannot be detected: I2S is one-way).
2. UART keys: `w`/`s` scroll, `e` select, `m` back, `a`/`d` left/right (volume on the Test tone screen), `p` play/pause.
3. Home: `s` x3 to Extras, `e`; `s` to Test tone, `e`. Select (`e`) on **1 kHz tone**. You should hear a quiet tone;
   `d` raises the volume 1 step = 2 dB. Try the "phones" jack (gain switch low first) and the "line out" jack. If nothing is
   audible see [Mute line](#mute-line-gp22) — the polarity is confirmed, so do not flip `NEUPOD_AUDIO_UNMUTE_LEVEL`.
4. `e` again stops it. Try **L/R ident** (left ear first), then **Scale**.
5. Files: Extras > Files, a folder with a `.wav`, `.flac`, `.mp3` or `.m4a`, Select. Now Playing opens with the tags and format badge; the wheel (`w`/`s`) is volume; `p` pauses; `m` goes back
   while it keeps playing. `d` (Right) on a `.flac` runs the MD5 verify instead of playing. An `.m4a` with AAC says "AAC not supported yet".
6. The UART prints every 10 s the `audio:` line (underruns must stay 0) and the `audio sink:` line
   (actual rate, divider, `dma_underruns`, mute state, source, volume).

## Not verified on hardware

Everything in this page about the board's behaviour is from reading the datasheet-level behaviour of the RP2350 PIO and
DMA and from the host build; none of it has been run on the Audio Pack. The 1 kHz tone on the Audio Pack is verified (3 Nov 2026). Specifically open: the
DMA interrupt timing under UI load, clock jitter, 88.2/96 kHz, SD streaming throughput at 24/32-bit, the decoders' CPU load and flash-cache behaviour on the RP2350, the 16 KB core-1 stack margin under MP3 (watch `core1_stack_free` in the `audio:` line), and the real RAM headroom (about 28 KB were left in the link).
